## 2026-11-21

- **The owner's second review of Phase 1 applied** (decision 41 of the design plan):
  - *Install*: only `mlxf.mod` and the library are installed. A consumer's `use mlxf` compiles, links and
    runs on the GPU. `use mlxf_array` and `use mlxf_c_array` do not compile.
  - *Layout*: `src/core/runtime/` and `src/core/array/`, still one library target. `mlxf_array` is now a
    parent module (the type, its generics and the interfaces) with five implementation submodules:
    lifetime, transfer, borrow, evaluation and elementwise. This follows XEMA's search engine, and the
    split changes no behaviour.
  - *Entry*: every public procedure opens with the entry before it touches an operand. New rule `entry` in
    `check_rules.py` found 48 procedures that did not, and it catches all five planted violations.
    `mlxf_handle` now only validates. Assignment, `kill` and finalization check the thread only when a
    handle is live, and `mlx_last_error` and `mlx_live_count` are guarded. `object_contracts` has four new
    members: an empty evaluation list, `mlx_live_count` and `mlx_last_error`, each called inside a parallel
    region, and a live `firstprivate` copy released there.
  - *mlx_to_alloc*: allocates with `stat=`. A destination that cannot be allocated returns a status and a
    message. The test uses a lazy 1 PiB broadcast.
  - *Headless tests*: the memory limits skip without a device. The device test asserts only that selecting
    an absent GPU returns, because MLX 0.32 accepts it.
  - *Registry test*: the allocatable-component test also accepts a correct counted copy. The stale
    diagnosis is tested through `allocate(source=)`.
  - *Negative result*: gfortran 16.2 finalizes no OpenMP private copy. This holds for a `firstprivate`
    scalar and for an allocatable array of handles. The finalizer's guard is kept for compilers that do
    finalize these copies, but no member can reach it.
  - *Rebuilt*: Release now warned on `mlx_last_error` inside a compound logical expression, because the
    function is now impure. The testers assign the message to a variable first.
  - *Verified*: Debug and Release build with zero warnings and pass the fast gate (3 of 3, on the GPU). The
    headless gate (iokit denied, `MLXF_REQUIRE_GPU=OFF`) also passes 3 of 3.
- **Questions for Apple collected** (owner): `doc/collaboration/apple_questions.md`, 18 items in six groups
  (mlx-c packaging and API, devices and runtime, precision, SIMPLE's kernels, memory and threads, the
  collaboration), each with the question, where we saw it, and what we do meanwhile; sent in one chunk by the
  owner.
- **mlx-c's configure warning silenced at its one source** (owner, review of Phase 1): `MLXCConfig.cmake` of
  mlx-c 0.8.0 calls `find_package_handle_standard_args(MLX_C ...)` inside the package `MLXC`, and CMake printed
  a developer warning on every configure. `cmake/Dependencies.cmake` sets `FPHSA_NAME_MISMATCHED` around the
  one `find_package(MLXC ...)` and unsets it after (checked: a mismatch in another package still warns). The
  fix belongs upstream (pass `MLXC` as the name); the workaround goes when mlx-c ships it.

- **Exported = defs, local = stay** (owner, review of Phase 1; plan decision 40; the register's first rejection
  reversed). New `src/defs/mlxf_defs.f90` with `MLXF_HARD_ERROR_STATUS`, `MLX_DTYPES` and the vocabulary
  `MLX_DEVICES%cpu`, `%gpu`, which replaces the integers `MLX_CPU`, `MLX_GPU` in the public API. New rule
  `defs` in `scripts/check_rules.py` (a constant another module imports is declared in `src/defs`; a defs
  module is public by default, lists its imports as private, holds no procedures, imports only the generated
  layer). It fails on the tree before the move with the seven imports the move removed, and on five planted
  violations. `format_use_blocks.py` orders `src/defs` between the generated layer and `src/core`. Debug and
  Release build with zero warnings and pass the fast gate (3 of 3) through the build bridge.
- **Phase 1 of the design plan delivered** (run `mlxf_core`, M2 Ultra, unattended, under R4): the generated
  `bind(c)` layer (`scripts/gen_mlxc_bindings.py`: 673 interfaces and 7 skips equal the 680 names of the
  independent list on every build), `mlxf_libc`, `mlxf_error`, `mlxf_registry`, `mlxf_device`, `mlxf_memory`,
  `mlxf_array` and the user module `mlxf`; the leak gate (10,000 iterations of every supported form per
  device), the diagnosis gate and the recovery gate (a buffer beyond the maximum fails with a status, half the
  batch evaluates) pass on both devices in Debug and Release with zero warnings; the guard group
  `object_contracts` (four stops of the contract, each in a child) and the CTest budget of 3; rules `arity`
  and `ctorcall`; `doc/policies/binding_contract_policy.md` and the skill `mlxf-binding`. Measured: a registry
  check costs under 10 ns per operand; Metal took every `mlx_alloc` buffer from 1 KiB to 64 MiB without a
  copy. One deviation: the generated types are one module, because mlx-c's headers refer to each other's
  types in a cycle.
- **Ruling R4: the answer to the Phase 1 stop** (owner; decision 39 of the design plan): no procedure has more
  than five dummy arguments (a spec type beyond; the owner's house rule, rule `arity`); list arguments are
  arrays of handles; decision 8 is widened by the three gfortran defects (no function reference inside an
  array constructor of handles, rule `ctorcall`; no whole-array assignment of a function result to an array
  of handles; no self-assignment of a derived type holding handles), the leak gate keeping their supported
  forms; `mlx_live_count()` is public; the reproducers join `doc/compiler_issues/`, and no gate pins a compiler
  defect.
- **Phase 1 of the design plan stopped at its probes** (run `mlxf_core`; negative result): GNU Fortran 16.2
  (and 13.4) leaves function results in array constructors and a scalar function result assigned to a whole
  array through an elemental defined assignment unfinalized, and finalizes the right side of an intrinsic
  self-assignment of a type with finalizable components before reading it. With decision 8's reference counts
  these are two leaks and a double release in cases its leak gate covers; the plan's Progress gives the
  reproducers and four alternatives for the owner's ruling. No library code was written.
- **Phase 0 of the design plan delivered** (run `mlxf_core`, M2 Ultra, unattended; measurement only, no source
  edited): the machine, toolchain and Homebrew's shared MLX 0.32.4 / mlx-c 0.8.0 recorded; mlx-c's C examples,
  a custom Metal kernel included, run on the GPU; the scaffold builds and gates in Debug and Release with one
  GPU device visible from the run's session. SIMPLE `5709265cb`'s `polar_matching_bench`, twice per case:
  `matrix_t` 2.9e6 pairs per second at 24 threads (2.6e6 on the 16 performance cores), `per_pair` 1.2e6, spread
  at most 2 % at the full teams; its check suite reproduces the 3 minimising-rotation disagreements in 320,000
  pairs. SIMPLE's particle-image FFTs are single-threaded `FFTW_ESTIMATE` plans inside OpenMP loops over
  particles. f of decision 28 is 0.23 (the plan's Progress has the numbers).
